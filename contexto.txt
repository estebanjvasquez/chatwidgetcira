3. ARQUITECTURA DEL BOT (resumen del flujo Actual)
────────────────────────────────────────────────────────────────────────────────

Webhook (POST /cira-botV2) → Pre-Procesing3 (extrae chatInput, sessionId)
→ Admin Password → Detect Command (/aprender, /listar-aprendizajes, /borrar-aprendizaje)
→ Is Command?
   TRUE  → Validate Password → Route Command → INSERT/SELECT/UPDATE agent_learnings
   FALSE → Load Learnings (SELECT categoria,instruccion FROM agent_learnings WHERE activo=1)
        → Build System Prompt (prompt base + aprendizajes)
        → Interactive Intent Agent3 (Gemini, temp 0.1; tools Catalog Sectores2 / Servicios2;
          memoria Postgres sessionId_intent)
        → Parse Intent JSON3 (limpia markdown, JSON.parse, regex de rescate)
        → Is Search Ready?3
             TRUE  → MySQL Query3 (SELECT ... FROM ChatView WHERE {whereClause} LIMIT 100)
                   → If2 (¿vacío?) → Code in JavaScript1 (no encontramos) / Format Cards2 (tarjetas)
                   → Final Respond3 → Edit Fields1 → Call 'CIRA_log' (logging)
             FALSE → Respond Conversation5 (texto conversacional)

Salida: { output: HTML, type: 'results' | 'conversation' }

El prompt pide al modelo devolver JSON en una línea:
  {"whereClause","queryIntent","hasFilter","needsClarification","isSearchReady","humanSummary"}
Reglas SQL: Sector/Servicios SIEMPRE con LIKE (multi-valor), name con LIKE, rif exacto.

4. DIAGNÓSTICO — CAUSAS RAÍZ DE LOS FALLOS
────────────────────────────────────────────────────────────────────────────────

HALLAZGO TRANSVERSAL: el dashboard SOBREESTIMA errores. Marca como "inválido" toda salida
que no sea JSON parseable, pero muchas son respuestas conversacionales CORRECTAS.

Segmentación por fecha (dos "eras"):
  [INTENT:...] tags      267 filas  mar–abr  → PROMPT LEGADO (ya no existe). Ignorar.
  Texto/lenguaje natural  94 filas  mar–abr  → mayormente legado; patrón reproducible
  Respuesta vacía         13 filas  25-mar   → legado
  "Te refieres" ambiguas 340 filas  abr–may  → ARQUITECTURA ACTUAL (problema real)
  Bad escaped character    3 filas  abr–may  → ACTUAL (apóstrofes rompen JSON)

PROBLEMA 1 (dominante): bucle "¿Te refieres a alguna de estas?"
  - 340 casos, TODOS query_intent=COMPANY, TODOS resultados_encontrados=1.
  - Casi todos vienen del clic en tarjeta: sendPrompt('dame información sobre la empresa X').
  - Causa: nodo Format Cards2, rama isFullCard (COMPANY/RIF) tiene el header hardcodeado
    "¿Te refieres a alguna de estas?" incluso con 1 solo resultado exacto.

PROBLEMA 2: apóstrofes rompen el JSON (KALA'S, C.A.)
  - El modelo genera LOWER('%KALA\'S%'); \' es escape inválido en JSON → JSON.parse falla.

PROBLEMA 3: saluda o dice "no encontramos" cuando el término SÍ es válido
  - CONSTRUCCION, SERVICIOS A POZOS, POZOS, FABRICANTES, MOVIMIENTO DE TIERRA (existe en
    catálogo, servicio id 85) → el modelo respondió con el saludo genérico en vez de buscar.

PROBLEMA 4: menú "A) empresa … B) sector …" (≈19-25 casos)
  - Ante términos ambiguos el modelo devuelve un menú de texto → rompe JSON y molesta.

PROBLEMA 5 (legado): drift de formato ([INTENT:X], texto plano). Ya no aplica al bot actual.

Aprendizajes de los catálogos:
  - Solo 8 sectores (estables desde 2022) → conviene incrustarlos en el prompt.
  - abogados vs legal: "legal" encontró 6, "abogados" dio 0 porque el bot buscaba solo en
    Sector/Servicios y NO en name (varias empresas llevan "ABOGADOS" en el nombre).
    → Regla general: en búsquedas por concepto, buscar también en name por raíz.
  - gruas/izaje/elevación NO tienen match en el catálogo → "no encontramos" es correcto.
  - "X" y "OTROS" son basura a excluir como criterio.

REGLAS DE EXCLUSIÓN (falsos positivos):
  FP-1  formato legado [INTENT:...]      respuesta_ia ~* '^\s*\[(intent|needs_clar)'
  FP-2  input vacío                      TRIM(pregunta_usuario) = ''
  FP-3  conversacional legítima          saludo / fuera de ámbito / "debe limitar su búsqueda"
        (OJO: "no encontramos" YA NO va aquí; ver categoría accionable)
  FP-4  detalle de 1 empresa             (query_intent='COMPANY' AND resultados=1)
                                          OR pregunta ILIKE 'dame informaci%n sobre la empresa%'

MÉTRICA DE AMBIGÜEDAD — CORRECCIÓN IMPORTANTE:
  La señal 'output contiene "Te refieres"' es INCORRECTA (da 0 real, era detalle de 1 empresa).
  Ambigüedad real = needs_clarification_ai=TRUE OR patrón "puede referirse/interpretarse" /
  "A)...B)" / "[NEEDS_CLARIFICATION". En el histórico ≈25 casos (menú A/B, comportamiento viejo).

CATEGORÍA NUEVA Y ACCIONABLE — "Consultas sin resultado" (brecha de vocabulario / sinónimo):
  NO descartar "%no encontr%". Agruparla por término, cruzarla contra sectors/services y
  ordenar por frecuencia. Clasificación automática:
    🔴 BUG        coincide con catálogo pero dio 0  → ej: operadores (4×), instalaciones marinas,
                  riesgos, gasoductos, registros y perfiles  (revisar where o dato en ChatView)
    🟡 SINÓNIMO   no coincide, término de negocio    → ej: gruas, alquiler de gruas, levantamiento, fianzas
    ⚪ RUIDO      typo/gibberish/nombre propio        → ej: grafox, b, whtherfor, trnsporte
  (44 filas de "no encontramos" en el histórico. Query SQL con EXISTS contra sectors/services
   y ranking por 'veces' incluida en el doc.)

MEJORA DE FONDO recomendada: dejar de adivinar por texto. Agregar al logger (CIRA_log /
Edit Fields1) las columnas resultado_tipo (results|conversation|sin_resultados|comando|error),
parse_ok, es_error_real. Luego el dashboard filtra por es_error_real=TRUE.

7. ANÁLISIS DE SINÓNIMOS (decisión tomada)
────────────────────────────────────────────────────────────────────────────────

Pregunta: ¿el mecanismo de "aprendizajes" (/aprender) sirve para sinónimos?
  - SÍ técnicamente: /aprender CIRA2024 SINONIMOS: ... se inyecta en el prompt. Cero cambios.
  - NO óptimo a escala: cada sinónimo infla el prompt (~2000 tokens base) en CADA turno,
    es guía blanda (LLM decide), sin validación contra catálogo, y ensucia los aprendizajes.
  - Latencia: impacto bajo en Gemini Flash (el output domina); el costo/confiabilidad es lo crítico.

Opciones evaluadas:
  A) reusar /aprender          — 0 cambios, no escala (<15), no valida
  B) tabla synonyms dedicada   — comandos /sinonimo, /listar-sinonimos, /borrar-sinonimo,
                                 /validar-sinonimo (valida contra sectors/services) + nodo
                                 Load Synonyms que inyecta un diccionario compacto. RECOMENDADA.
  C) pre-expansión determinista— máxima confiabilidad/velocidad, pierde flexibilidad de frases.

Punto clave: la regla genérica "Búsqueda por concepto" (ya en MEJORADO) resuelve la MAYORÍA
de casos (ej. abogados) sin sinónimos. Los sinónimos solo hacen falta cuando la palabra del
usuario ≠ palabra de la BD (gruas→izaje). El universo real es pequeño.

DECISIÓN DEL USUARIO: por ahora NO crear subsistema de sinónimos. Usar la regla genérica y
afinar el dashboard (categoría "consultas sin resultado") para juntar data real y decidir
a futuro con evidencia.
